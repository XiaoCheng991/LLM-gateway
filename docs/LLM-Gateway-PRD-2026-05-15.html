产品概述

1.1 背景

企业使用大模型时，面临以下核心痛点：

  1. 多模型管理混乱 — 同一业务对比 OpenAI / Claude / DeepSeek / 本地模型，缺乏统一接入层
  2. 成本不可控 — 无法追踪每个 prompt 的 token 消耗、响应时间、成本分摊
  3. 质量无保障 — 模型升级后业务表现是否退化？缺少系统化评测手段
  4. 安全性缺失 — API Key 散落各处，Prompt 注入无防护
  5. 切换成本高 — 更换模型需修改代码，缺乏模型层抽象

1.2 目标

构建统一的企业级 LLM API Gateway，实现：

  1. 统一接入 — 对业务层屏蔽模型差异，提供一致的 OpenAI 兼容 API
  2. 成本可观测 — 全链路 token / 延迟 / 费用追踪
  3. 质量评测 — Prompt A/B 测试、模型对比、回归测试
  4. 安全保障 — API Key 集中管理 + Rate Limiting + Prompt 安全检测
  5. 可扩展 — 新增模型只需增加适配器，不侵入现有逻辑

1.3 目标用户

用户角色使用场景
Java 后端开发集成 LLM 能力到现有业务系统
AI 应用开发者测试不同模型 / Prompt 的效果对比
技术管理者查看成本报表、质量趋势
QA 工程师回归测试、Prompt 效果验证

🔍 选型策略

上述参考项目均为 Python / Node 实现。本项目选择 Java + Spring Boot 形成差异化：Java 21 虚拟线程原生支持高并发 I/O，Spring Boot 在企业级安全/监控/运维方面生态最为成熟，且与你的后端技能栈无缝衔接。

2.2 增强功能 (P1)

F6: Prompt 评测 (Eval)

  • 预置评测指标：响应长度、关键词匹配、格式验证
  • LLM-as-Judge 评测：用另一个大模型评估输出质量

  • 按 API Key / 用户 / 模型维度限流
  • Token 级别配额控制

  • Prompt 注入检测（基于规则或 LLM）

  • 审计日志：所有请求的完整链路追踪

3.2 设计原则

  1. 适配器模式 — LLMService 接口定义契约，各 Provider 实现 Adapter
  2. 工厂模式 — LLMServiceFactory 根据 modelId 动态返回对应实现
  3. 责任链模式 — 请求处理管线（Auth → Rate Limit → Validator → Router）
  4. OpenAPI 兼容 — 对外暴露 OpenAI 一致的 API 格式
  5. 无状态设计 — Gateway 层无状态，水平扩展只加实例

3.3 数据流

Client
  → POST /api/v1/chat/completions { model, messages, stream }
  → Auth Filter (校验 API Key)
  → Rate Limiter (检查配额)
  → Request Validator (参数校验)
  → Model Selector (根据 model 选择适配器)
  → LLMService.send() / stream()
    → Adapter 转换请求格式
    → HTTP 调用外部 LLM API
    → Adapter 转换响应格式
  → Metrics Collector (记录延迟 / token / 成本)
  → Response (JSON / SSE stream)
